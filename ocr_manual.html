How data flows through your model

Follow a single image of the word बहादुर from pixel on disk to predicted text.

Step 1 — Image on disk

A JPEG file. 483×293 pixels (or 824×294, or whatever the scanner produced). Three colour channels (RGB). Raw pixel values 0–255.

Step 2 — Transform

Your DataLoader's transform pipeline forces every image to the same shape:

Resize → (32 height, 128 width)
ToTensor → pixel values 0.0–1.0
Normalize → subtract ImageNet mean, divide by stdtransform

Result: a tensor of shape [3, 32, 128] — 3 channels × 32 pixels tall × 128 pixels wide.

Step 3 — Batch

The DataLoader stacks 64 of these together. Shape becomes [64, 3, 32, 128] — 64 images in one batch.

Step 4 — VGG16 CNN

The frozen VGG16 convolutional layers process the batch. Think of it as a very sophisticated edge and pattern detector. The image passes through 13 layers of convolution and pooling, each detecting increasingly abstract patterns — edges → strokes → curves → character parts.

Output shape: [64, 512, 1, 4] — 64 images, 512 feature channels, 1 pixel tall (pooled down), 4 positions wide.

Why does width become 4?

VGG16 has a specific architecture that downsamples the spatial dimensions. A 128-wide input shrinks to 4 wide after passing through all the pooling layers. Each of those 4 "columns" corresponds to roughly a quarter of the original image width — a rough spatial position.

Step 5 — AdaptiveAvgPool and reshape

f = self.pool(f)       # [64, 512, 1, 4]
f = f.squeeze(2)       # [64, 512, 4]
f = f.permute(2,0,1)   # [4, 64, 512]python

This reshape is the conceptual key to how CRNN works. We go from "a 2D image" to "a sequence of 4 feature vectors, each describing one horizontal slice of the image." The RNN will read these left to right, just like you read text.

Step 6 — BiLSTM

The sequence of 4 feature vectors gets fed into a bidirectional LSTM. It reads the sequence forward (left → right) and backward (right → left) simultaneously, capturing context from both directions for each position.

Output: [4, 64, 512] — 4 timesteps, 64 images, 512 features (256 forward + 256 backward).

Step 7 — FC layer → character probabilities

out = self.fc(r)   # [4, 64, 110]  (109 chars + 1 blank token)python

At each of the 4 timesteps, the model outputs a probability distribution over all 110 tokens (109 characters + 1 special blank token used by CTC).

Step 8 — CTC decoding

The greedy decoder takes those 4 timesteps of probability distributions, picks the highest-probability token at each step, collapses repeated characters, and strips blanks. The result is a string of predicted characters.

See the CTC section for a full worked example of why this is necessary.

Reading your training logs

What each number actually means, and how to know if training is healthy.

The numbers explained

train_loss

The average CTC loss across all training batches in the epoch. This measures how wrong the model's predictions were on the data it was trained on. You want this to go down every epoch — and it has, consistently: 1.175 → 0.039 over 21 epochs.

Warning sign

If train_loss goes to NaN (Not a Number), stop immediately. This means the gradients exploded — learning rate too high, or a numerical instability. Never let NaN training continue.

val_loss

The same CTC loss, but measured on the validation set — data the model has never seen during training. This is a more honest measure of how well the model actually learned, vs. just memorised.

The critical gap to watch

In your run, train_loss (0.039) is much lower than val_loss (0.42). The model performs better on training data than unseen data — this is normal and expected. It becomes a problem when val_loss stops improving or goes back up while train_loss keeps falling. That's called overfitting.

val_acc

Exact string match. The percentage of validation words where the model predicted every single character correctly. It's a strict metric — बहादुर predicted as बहदुर (one character off) counts as wrong.

Your current best: 57.88% at epoch 21. Over half of all validation words are now predicted perfectly.

val_cer (Character Error Rate)

A softer metric than val_acc. For each predicted/true pair, it computes the edit distance (how many insertions, deletions, or substitutions are needed to turn the prediction into the correct answer) and divides by the length of the correct answer.

  • CER = 0.0 → perfect prediction
  • CER = 0.379 → on average, the prediction needs edits on ~38% of characters
  • CER = 1.0 → the model is as wrong as if it predicted nothing
  • CER > 1.0 → actively worse than outputting blank (early epochs)

CER is more informative than val_acc at the early stages because it captures how close the model is, not just right/wrong.

lr (learning rate)

You saw the LR drop at epoch 20 from 1e-5 to 5e-6. This was ReduceLROnPlateau detecting that val_loss had plateaued for 3 epochs (epochs 16, 17, 18 all had similar val_loss). Halving the LR lets the optimizer take smaller, more precise steps — often unlocking further improvement. It worked: epoch 20 and 21 both hit new accuracy records.

What CNNs actually do

A Convolutional Neural Network (CNN) is a system that learns to detect visual patterns — at multiple scales, automatically, from examples.

The core idea: learned filters

Imagine a small window (say, 3×3 pixels) that slides across an image. At each position, it multiplies each of the 9 pixels it covers by a weight, and sums them up. The result is one number — a "response" measuring how much this patch of image matches the pattern the filter is looking for.

A filter with weights that highlight vertical edges will produce a high response wherever it finds a vertical stroke. A different filter finds horizontal edges. Another finds curves. The CNN doesn't decide which filters to use — it learns the filter weights from the training data.

Layers stack up

One convolutional layer applies many filters (64 or 128 or 512) and produces a feature map — a stack of responses, one per filter, across the whole image. The next layer applies filters to those feature maps, detecting patterns-in-patterns. By the time you're 13 layers deep (like VGG16), the filters are detecting things like "curved stroke with a dot above" or "horizontal bar with downstroke."

Pooling reduces size

Between convolutional layers, pooling layers shrink the spatial dimensions. A 2×2 max-pool takes the highest value in each 2×2 block and discards the rest — halving width and height. This is why your 128×32 image becomes 4×1 by the end of VGG16.

Why VGG16 specifically

VGG16 (Visual Geometry Group, 16 layers) was trained on ImageNet — 1.2 million photographs of 1000 categories. It learned incredibly general visual features: edges, textures, shapes, curves. These transfer to handwritten character recognition because both tasks fundamentally require detecting strokes and curves.

The frozen layers decision

Your notebook freezes VGG16's 14.7M parameters and only trains the BiLSTM + FC (3.2M parameters). This works because VGG16 features are already good enough for the CNN part — and freezing makes training ~5× faster while reducing the risk of overfitting on your dataset.

Where the magic disappears

A CNN is literally just matrix multiplications and non-linear activation functions (ReLU: max(0, x)), applied in a specific spatial pattern. There is no understanding of what a character "is." The model finds pixel-level correlations that happen to align with what humans call characters. It has no concept that "ब" is a letter — it only knows that images with certain pixel patterns tend to have the label "ब" in the training data.

Sequences and RNNs

The second half of your CRNN model. Once the CNN turns an image into a sequence of feature vectors, the RNN reads that sequence to produce text.

Why sequences at all?

Text has order. The character at position 3 depends on what came before it. A plain fully-connected network that looks at all features at once misses this temporal structure. An RNN processes one element at a time, passing a "memory" (hidden state) from step to step — so what it's seen before influences what it predicts next.

LSTM — the variant you're using

Basic RNNs have a problem: they forget things over long sequences. The Long Short-Term Memory (LSTM) architecture fixes this with learned gates — mechanisms that control what to keep in memory, what to forget, and what to output at each step.

An LSTM cell has three gates:

  • Forget gate: how much of the previous memory to discard
  • Input gate: what new information to add to memory
  • Output gate: what to read from memory as output

These are all learned from data. The LSTM figures out on its own what patterns are worth remembering across long sequences.

Bidirectional — why read both ways?

A standard LSTM reads left to right. A bidirectional LSTM runs two LSTMs simultaneously — one left-to-right and one right-to-left — and concatenates their outputs. At each position, the network has context from both directions.

For text recognition this matters: knowing what comes after a character helps disambiguate what it is. The end of the word helps confirm the reading of the beginning.

In your model specifically

self.rnn = nn.LSTM(
    input_size = 512,      # features from VGG16
    hidden_size = 256,     # memory size per direction
    num_layers = 2,        # two stacked LSTM layers
    bidirectional = True,  # forward + backward
    dropout = 0.3          # randomly disable 30% of neurons during training
)python

Two stacked LSTM layers means the output of the first LSTM becomes the input to the second — deeper, more abstract sequence modelling. Dropout randomly zeroes 30% of activations during training to prevent overfitting.

CTC loss explained

CTC (Connectionist Temporal Classification) is probably the hardest concept in your notebook. Here it is made concrete.

The core problem

Your model processes a 128-pixel-wide image and produces, after all the CNN and RNN processing, a sequence of 4 outputs. The label for that image might be जोख — 3 characters. How do you train a model that produces 4 outputs to match a 3-character target? And what if the image is बहादुर (6 characters) — also produces 4 outputs? How does 4 outputs encode 6 characters?

This is the alignment problem: the number of model output timesteps doesn't match the number of characters in the label, and you don't know which output timestep corresponds to which character.

CTC's solution: the blank token

CTC introduces a special blank token (let's call it _). The model can now output blanks between real characters, allowing different length sequences to encode the same label:

ज ो ख _    →  collapses to:  जोख
ज _ ो ख    →  collapses to:  जोख
_ ज ो ख    →  collapses to:  जोखdecoding

The decoding rules are:

  1. Merge consecutive repeated characters (जज → ज, but ज_ज → जज since the blank separates two separate जs)
  2. Remove all blank tokens

What CTC loss actually computes

For a given image, there are many valid output sequences that all decode to the correct label. CTC loss sums the probability of all valid alignments — and trains the model to maximise this total probability. You don't need to know which alignment is correct, only that the correct label should be producible.

As training proceeds, the model learns to assign high probability to the sequences of tokens that, after collapsing, produce the correct words. It figures out the alignment entirely on its own from the image-label pairs.

The greedy decoder in Cell 11

def decode(output):
    argmax = output.argmax(dim=2)     # pick highest-prob token each step
    result = []
    for sequence in argmax:
        chars = []
        prev = None
        for token in sequence:
            if token != blank and token != prev:
                chars.append(idx2char[token.item()])
            prev = token
        result.append(''.join(chars))
    return resultpython

This is CTC greedy decoding: at each timestep, pick the most probable token, then collapse repeats and strip blanks. It's not the theoretically optimal decoder (beam search is better), but it's fast and works well enough for evaluation during training.

Why the loss can go above 1.0

CTC loss is measured in nats (natural log units), not a percentage. A loss of 1.175 (your epoch 1) means the model assigns about e^-1.175 ≈ 31% probability to all correct alignments combined. A loss of 0.039 (epoch 21) means it assigns e^-0.039 ≈ 96% probability to the correct alignments. The loss is essentially measuring how surprised the model is by the correct answer.

Transfer learning

The technique behind your model's fast learning — and why it started at 16.78% accuracy in epoch 1 instead of near 0%.

The basic idea

Training a deep neural network from scratch requires enormous amounts of data and compute. But most visual tasks share common low-level features: edges, curves, textures. Instead of re-learning these from scratch for every new task, you start with a model that already learned them on a large dataset, and adapt it to your specific task.

What "pretrained" means

VGG16 was trained on 1.2 million images spanning 1000 categories — cats, cars, furniture, animals. After that training, its convolutional filters encode extraordinarily general visual representations. These representations happen to be useful for detecting handwritten strokes too.

Two strategies: freeze vs. fine-tune

Freeze (what your notebook does): Lock the pretrained CNN weights. Only the new layers on top (BiLSTM + FC) are trained. Fast, less data needed, works when the source and target domains are reasonably similar.

Fine-tune: Unlock the pretrained weights and train the whole model, but at a much lower learning rate for the pretrained parts. Slower, needs more data, but can adapt the features more specifically to the new domain.

Why freeze makes sense for Phase 1

You're training on Hindi handwriting (source domain) to build a base, then fine-tuning on synthetic Nepali words (target domain). Freezing VGG16 in Phase 1 makes training faster and prevents the large pretrained network from overfitting your 69k dataset. In Phase 2, you might consider unfreezing the last few VGG layers for Nepali-specific adaptation — though given your time constraint, keeping it frozen is also fine.

Why this explains your epoch 1 results

Your 20k-subsample run got 0.06% accuracy at epoch 1. Your full-dataset run (same model, more data) got 16.78%. The difference isn't the model architecture — it's data volume. More training examples → more diverse character combinations → faster convergence → better generalisation from the very first epoch. Transfer learning gave you the feature extraction for free; data volume determines how fast the BiLSTM learns to use those features for your specific task.

Problem definition (often 20% of total time)

What exactly needs to be predicted? What counts as success? What's the cost of a wrong answer? A land registry OCR system where a wrong address corrupts legal records needs a different accuracy bar than a casual text transcription app. In industry, ML engineers spend significant time negotiating these requirements before writing any code.

Data collection and cleaning (often 40–60% of total time)

This is the unglamorous majority of real ML work. Finding data, cleaning it, labelling it, auditing it, handling edge cases, dealing with imbalanced classes. You hit this directly: path resolution issues, the রুকুম (পূর্বী ভাগ) parenthetical edge case, short words with rare vowel combinations.

In production, companies often spend months and significant budget just on data labelling — paying human annotators to produce the ground-truth labels that make training possible.

Baseline model

Before building anything complex, good ML engineers establish a baseline — the simplest thing that could possibly work. Sometimes the baseline is already good enough. Your CRNN+CTC is actually a well-established, proven architecture for text recognition — it's not bleeding-edge, which is a feature not a bug for a real use case. Proven architectures are more predictable and easier to debug than novel ones.

Iteration

Training once and deploying is rare. Real development involves repeated cycles of: train → evaluate → identify failure modes → fix (more data, different architecture, better preprocessing) → retrain. Your two-phase approach (Hindi pretrain → Nepali fine-tune) is an example of this.

Deployment

Getting a model from a Jupyter notebook to a production API involves: serialising the model weights (your .pth files), building an inference server, handling batching for throughput, versioning, rollback capability, and usually containerisation (Docker).

Monitoring

Models degrade in production. Handwriting styles change, new document formats appear, edge cases accumulate. Production ML systems track accuracy metrics on live data and alert when performance degrades below thresholds.

What ML engineers actually spend time on

Based on real surveys of ML practitioners:

  • ~40% — data work (collection, cleaning, labelling, augmentation)
  • ~20% — debugging (shape mismatches, path errors, CUDA issues — exactly what you've been doing)
  • ~20% — infrastructure (setting up environments, managing compute, deployment)
  • ~15% — experimentation (trying different architectures, hyperparameters)
  • ~5% — the "AI magic" that movies show
